topic: Two-factor authentication with authenticator apps
updated: 2026-11-26T08:37
---


- (decision) Scope: TOTP authenticator apps (RFC 6238) only; SMS, email codes, WebAuthn as a second factor, remember-this-device are out (owner request 2026-11-26).
- (requirement) R14: a user with a password, or who signs in by an external provider, adds an authenticator app by scanning a QR code or typing the key; enrolment completes only after a current code is entered.
- (requirement) R15: on completing enrolment the user sees ten single-use recovery codes once; regenerating them invalidates the earlier set.
- (requirement) R16: password and provider sign-in for an account with 2FA creates a session only after a current code or an unused recovery code.
- (requirement) R17: passkey sign-in is unchanged; no second step is asked of passkey sign-in.
- (requirement) R18: an admin sets 2FA per install to off, optional, or required; the setting applies at the next sign-in.
- (requirement) R19: a user disables 2FA after a current code or a recovery code; an admin resets a user's 2FA so the user can enrol again.
- (constraint) TOTP seeds are encrypted with TALEART_SECRET_KEY, as provider secrets are; losing the key means users re-enrol.
- (constraint) Recovery codes are stored only as hashes; a TOTP code is accepted once per 30-second window (replay); one step of clock tolerance either side.
- (constraint) A failed second-step code counts toward the same per-username throttle as a wrong password (sign-in spec, Password rules).
- (question) For required mode: do existing password or provider users who have not enrolled get blocked at sign-in until they enrol, or are prompted after sign-in?
- (question) Admin reset of a user's 2FA: directly by the admin, or a one-time link like the password reset?
- (assumption) R14 to R19 extend the initiative's numbering after R13; initiative-taleart.md needs the new requirement lines when this epic is adopted.
- (event) Spec drafted from the owner's request and sign-in-methods spec; self-validate pending.
- (event) Pass 1 coherence: each requirement states what shows it was met; constraints bend the design; boundaries name SMS, email, WebAuthn-as-factor and remember-device as out; open questions are not answered by invention.
- (event) Pass 2 preservation: the owner request and the sign-in-methods spec are the sources; nothing load-bearing dropped.
- (decision) 2FA enrolment uses a QR code (the manual key stays available as the fallback); the owner chose QR code (2026-11-26).
- (decision) 2FA is self-service: a user enrols, regenerates recovery codes and disables 2FA on their own account; no admin reset is part of this epic (owner, 2026-11-26). Supersedes the admin-reset question.
- (decision) Required mode blocks sign-in for users without 2FA until they enrol: after the correct password or provider sign-in they are taken through enrolment (QR code, recovery codes) before any session exists; admins included (owner chose option A, 2026-11-27). Supersedes the required-mode open question.
