## Intent

**Problem:** A tale is full-screen media (PRD FR-010), but tales have only a title, and there is no media storage yet (AD-11).

**Approach:** Add a `storage` module with a media storage port (put, get, delete by key) and a local-disk adapter. A user picks an image, GIF or video for a tale in the dashboard; the API checks its type and size, stores it through the port, and saves the storage key on the tale. Tale cards and the tale drawer show the media.

## Boundaries & Constraints

**Always:** Content stores the storage key only, never a path or URL (AD-11); the API derives the URL. Accepted types: `image/jpeg`, `image/png`, `image/webp`, `image/gif` up to 10 MB; `video/mp4`, `video/webm` up to 100 MB. The declared `Content-Type` must match the file's leading bytes (magic number); otherwise 415. Keys are generated by the server (`tales/<uuid>.<ext>`), never from the client's file name. Replacing media stores the new file, updates the tale, then deletes the old file. The local adapter writes under `MEDIA_DIR` (env, default `.data/media` at the repo root, gitignored) and refuses any key that would escape it. Errors use the standard body; a too-large body is 413 `media_too_large`, never 500. Tests use a temporary `MEDIA_DIR` and the `taleart_test` database. Module rules from stories 11 and 3 hold (own tables, public `index.ts`, `type:server-module`, contract first). The dashboard follows the story 14 design system.

**Never:** Transcoding, thumbnails, cropping or image processing. Object storage adapters (S3 and the like). Deleting tales. Serving media through the Delivery API (web zones epic). Accepting a URL instead of a file.

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|--------------|---------------------------|----------------|
| Upload image | `PUT /api/v1/tales/{taleId}/media`, body = file bytes, `Content-Type: image/png` | 200 tale with `media: {kind: "image", contentType: "image/png", url: "/api/v1/tales/{taleId}/media"}` | — |
| Upload video | same with `video/mp4` | 200, `media.kind` = `video` | — |
| Read media | `GET /api/v1/tales/{taleId}/media` | 200, the stored bytes with the stored `Content-Type` | 404 `media_not_found` when the tale has none |
| Tale lists | `GET /zones/{zoneId}/tale-groups` | each tale carries `media` or `null` | — |
| Replace | upload again | new media served; old file removed from `MEDIA_DIR` | — |
| Unsupported type | `Content-Type: application/pdf`, or `image/png` with non-PNG bytes | 415 | `unsupported_media_type` |
| Too large | image over 10 MB or video over 100 MB | 413 | `media_too_large` |
| Empty body | 0 bytes | 400 | `validation_failed` |
| Unknown tale | missing or non-UUID id | 404 | `tale_not_found` |
| Restart | upload, restart the API | media still served | — |

## Implementation Notes

- Contract owns the media rules shared by API and dashboard: `MEDIA_CONTENT_TYPES`, `MAX_IMAGE_BYTES`, `MAX_VIDEO_BYTES`, `mediaKind`, `maxMediaBytes`, `taleMediaUrl`. The tales module maps `media` with them; the storage key never leaves the module except through `getTaleMedia` / `setTaleMedia`.
- PUT order: tale (404), declared type (415, before the body is read), body (raw, 100 MB cap → 413), empty (400), per-kind size (413), magic number (415), then store → update row → delete old file (cleanup failures are logged, not returned).
- `entity.too.large` maps to 413 `media_too_large` on `/media` paths and 413 `validation_failed` elsewhere (an oversized JSON body is not media).
- GET sends `Cache-Control: no-cache` with the key as ETag; the dashboard appends `?v=<n>` after an upload so a replaced file at the same URL reloads.
- The "Tale" drawer is a `taleMedia` case of the existing create drawer. If "Add tale" saves the tale but its file is refused, the drawer switches to that tale with the API message.
- `MEDIA_DIR` defaults to `.data/media` resolved from the API's working directory (the repo root under `nx serve`).

## Design Notes

Sniffing needs only the first bytes: PNG `89 50 4E 47`, JPEG `FF D8 FF`, GIF `47 49 46 38`, WebP `RIFF....WEBP`, MP4 `....ftyp` at offset 4, WebM `1A 45 DF A3`. `kind` is `image` for the four image types (GIF included) and `video` for the two video types. The API keeps the body in memory for this slice (100 MB cap); streaming uploads can come with object storage.
